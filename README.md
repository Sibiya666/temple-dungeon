## Архитектура ядра

`Dialoid.Core` — одна сборка; пространства имён ниже — это модули, а не строгие слои: часть из них ссылается друг на друга.

- **Stats** — фундамент, ни от чего не зависит: статы, модификаторы Flat/Increased/More/Override, формула, граф зависимостей `per`, условия.
- **Effects** — эффекты узлов, области действия, интерфейс механик `IMechanic` (параметры, допустимые области, хуки) и реестр. Реестр по умолчанию регистрирует каталог из **Mechanics**, а контексты хуков используют типы **Simulation** — эти модули связаны в обе стороны.
- **Character / Passives / Skills** — билд и его правила (`BuildRules`), компиляция персонажа, дерево пассивок, деревья и компиляция скиллов.
- **Data** — загрузка JSON из `data/` и валидатор с русскими сообщениями (файл, id, причина). Определения контента живут в модулях, которые их используют, поэтому Data зависит от типов Character, Combat, Effects, Passives, Skills и Simulation (например, `DummyDefinition`), а они — от `GameData`.
- **Combat** — базовый урон, конверсия, митигация, попадание, недуги. Combat и Simulation делят `AilmentInstance` (тип лежит в Simulation, Combat его создаёт).
- **Mechanics** — механики классов и ключевых узлов (C#, подключаются по id из данных).
- **Simulation** — детерминированная симуляция боя («среднее» и случайный режим, защитный режим с атакующим манекеном).
- **Builds** — экспорт и импорт билда: код `DLD1:` + base64url(gzip(JSON)), JSON в snake_case.

Загрузка данных проверяет всё, что движок читает по имени: обязательные статы (`RequiredStats`), каталог тегов (плюс динамический `skill:<id>`), ссылки на скиллы, баффы и узлы, параметры поведения (`BehaviorKeys`), параметры и области механик. Новый скилл или узел, собранный из существующих эффектов, условий и механик, добавляется только данными, без правок C#.

### Дополнения движка к спецификации

Записаны здесь, как просит спецификация:

- условие `target_frozen` (цель под заморозкой; нужно «Расколу»);
- механика `blood_feast` — «Кровавый пир»: +1% скорости атаки за стак кровотечения на основной цели, максимум 15% (стат-часть — обычный модификатор `bleed_max_stacks`);
- механика `ground_type` — тип урона наземной зоны скилла («грозовая земля» «Разряда» — молния даже на физическом скилле);
- механика `chill_slow` — сила охлаждения вместо стандартных 15% (у «Вечной мерзлоты» 25%);
- песочное правило `spread_ignite`: в паке поджог, наложенный использованием, через `delay` (1 с) считается наложенным на все живые цели пака, которых он не достал (позиций в песочнице нет, поэтому «передача соседям при смерти» не моделируется);
- песочное правило `fire_armor`: если в слотах есть скилл, создающий горящую землю (`ground_duration` и `ground_fraction` > 0, огненная зона), персонаж получает +30% брони (Increased) и +10 к максимуму сопротивления огню.
- тип урона «тьма» (`DamageType.Dark = 5`, последний в порядке конверсии, не стихия): отклонение от спеки ядра 6.2 (там пять типов). Конверсия в тьму возможна из любого типа, из тьмы — никуда. «Каменная кожа» бронирует только стихийные удары и яд (`DamageTypes.IsElemental`), тьму не бронирует. Места: `DamageType`, `DamageTypes`, `RequiredStats`, `EffectJsonConverter`, `CombatEngine` (правило брони), `Reckless`, `NumberLine`, `CharacterSheet`, `Sandbox/Texts`; данные: `stats`, `tags`, `attributes` (Интеллект даёт `resist_dark`), `dummies` (сопротивление тьме равно яду), баффы `steel_will` и `phase_barrier`.

## Контент

Что есть в `data/`:

- два класса (Воитель, Чародей), по шесть основных скиллов с деревьями развилок (плюс производные мини-скиллы: Возвращающийся топор, Огненный взрыв, Вспышка телепорта — `returning_axe`, `fireball_blast`, `blink_flare`), один скилл из лута (Ядовитый туман, `poison_cloud`);
- пассивное дерево и 6 keystones, четыре асцендента (Берсерк, Громовержец, Пироман, Криомант) по 6 notables;
- атрибуты, оружие, предметы, манекены («Тренировочный», «Рой», «Босс», «Атакующий босс»);
- эталонные билды в `data/builds/` (шесть основных 60 уровня, версии 20 уровня, паритет, пары для keystones; сводка с метриками — `data/builds/README.md`).

**Статус классов (2026-10-31):** Воитель и Чародей — архивные технические прототипы. Их скиллы, билды и тесты сохраняются без переработки. Актуальную разработку классов начинаем с Мечника в его отдельной зоне; это отдельный дизайн, а не переименование Воителя.

Как добавить контент: всё, что собирается из существующих эффектов, условий и механик, добавляется только JSON-файлами в `data/`, без правок C#. Формат каждого каталога, список стат, тегов и механик — в [справочнике автора данных](docs/data-authoring-reference.md). Загрузчик строгий: неизвестное поле или ссылка на несуществующий id — ошибка загрузки на русском (файл, id, причина). Каждое отклонение от числа спеки записывается в `data/BALANCE_NOTES.md`.

Тесты контента и баланса (`core/Dialoid.Core.Tests/Content/`):

```bash
# все тесты, включая приемку баланса (режим Average)
dotnet test core/Dialoid.sln
# только контент и баланс
dotnet test core/Dialoid.Core.Tests --filter "FullyQualifiedName~Dialoid.Core.Tests.Content"
# все метрики приемки одной таблицей
dotnet build tools/BuildOptimizer -c Release
dotnet tools/BuildOptimizer/bin/Release/net8.0/BuildOptimizer.dll suite --all
```

Пересборка эталонных билдов после изменения чисел: `tools/BuildOptimizer/rebuild_references.sh` (инструмент разработчика вне решения; запускать только последовательно, полная пересборка около 1,5 часа). После нее проверить diff в `data/builds/`, прогнать тесты и обновить метрики в `data/builds/README.md` (таблицы собраны из вывода `suite --all`).

## Отладочная сцена

Godot-проект `game/` — тренировочная комната (план 4, спека `docs/superpowers/specs/2026-10-29-dialoid-training-room-design.md`): 3D-комната подземелья с героем и манекеном, живой бой по правилам ядра и окна поверх боя. Это тонкий слой отрисовки над `Dialoid.Sandbox`: перезарядка, ресурс, урон, баффы — в ядре, досягаемость, сегменты и измеритель — в песочнице. Интерфейс строится кодом в `Main._Ready()`. Окна (клавиша — окно): C «Персонаж», P «Пассивки», N «Асцендант», K «Скиллы», B «Билды», R «Разбор», M «Симуляция» (мгновенный замер минуты боя), T «Измеритель», L «Журнал», G «Графики»; Esc закрывает верхнее окно. Кнопки окон и выбор манекена — на верхней панели. Рендерер Forward+, физика 3D — Jolt Physics.

Разработка и приемка идут на Windows (PowerShell 5.1). Нужен Godot 4.7 .NET, консольная сборка `Godot_v4.7.2-stable_mono_win64_console.exe` (версия `Godot.NET.Sdk` в `game/Dialoid.Game.csproj` совпадает с редактором), и .NET SDK (`dotnet`). Где ищется Godot: переменная `GODOT`, иначе `C:\Users\sibiya666\Tools\Godot_v4.7.2-stable_mono_win64\Godot_v4.7.2-stable_mono_win64_console.exe`, иначе `godot` из PATH. Другой путь:

```powershell

```

Запуск: открыть `game/project.godot` в редакторе Godot и нажать «Запустить» (F5) — или из корня репозитория:


### Ассеты комнаты

Модели, анимации и текстуры в git не кладутся (лицензии). Сцена ищет их в папке из переменной `DIALOID_ASSETS`, иначе в `assets/` в корне репозитория (она в `.gitignore`). Таблица «id → файл» — `game/data/assets.json` (имена файлов как на диске). Перед импортом `tools/godot_check.ps1` вызывает `tools/sync_assets.ps1`: он копирует в `game/vendor/` (вне git) **только файлы из таблицы**, если их там нет или исходник новее, с нормализованными именами (нижний регистр, пробелы и скобки → `_`: `sword and shield slash (2).fbx` → `sword_and_shield_slash_2.fbx`), печатает отсутствующие и предупреждает, если нет учета лицензий `LICENSES.md`. Файл, исчезнувший из ассетов, убирается и из `game/vendor/`. Вручную:

```powershell
$env:DIALOID_ASSETS = 'D:\dialoid-assets'   # не обязательно: по умолчанию assets/ в корне
powershell -NoProfile -ExecutionPolicy Bypass -File tools/sync_assets.ps1
```

Без ассетов комната рисуется заглушками (капсулы того же роста, однотонные материалы), самопроверка проходит. На каждый отсутствующий файл в логе одна строка `ASSET_MISSING: …` (не `ERROR`). Настройки импорта FBX не хранятся в `.import` (папка вне git): имя клипа берется из имени файла (в Mixamo все клипы называются `mixamo.com`), зацикливание стойки, ходьбы и бега, прибитый корень (у бедер обнуляются X и Z), перепись путей костей под скелет модели (`mixamorig:`, `mixamorig1:`, … ) и масштаб по измеренной высоте модели делаются в коде (`game/Room/AssetLibrary.cs`). Текстурам скрипт пишет `.import` со сжатием VRAM и мипмапами.

Учет лицензий — `assets/LICENSES.md` (вне git, лежит рядом с ассетами). Без него сборки с ассетами не публикуются:

- **Mixamo (Adobe)** — персонажи и анимации выше. Условия: бесплатно для коммерческой игры, без роялти и атрибуции, но сами файлы раздавать или продавать как ассеты нельзя (FAQ Adobe: https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html). Поэтому модели и клипы попадают к игроку только внутри экспортированного `.pck` в составе игры (так разрешено), а FBX отдельно не раздаются и не кладутся в git;
- **Poly Haven** — текстуры `monastery_stone_floor`, `castle_wall_slates`, `medieval_blocks_02`, `medieval_wood`: CC0 (https://polyhaven.com/license), страницы текстур — в учете;
- **кровь** на полу — процедурная текстура, рисуется в коде (`game/Room/RoomView.cs`), внешнего источника нет;
- значки кнопок геймпада Kenney Input Prompts (CC0) пока не подключены: вместо них текст «[A]» (см. «Отложено»).

Качество графики: по умолчанию высокое; `-- --quality low` (минимальные требования: GTX 1050 Ti / RX 560, 1080p ≥ 30 кадров/с) выключает SSAO, тени факелов, объемный туман и свет снарядов — остаются тень героя и контур.

### Управление: клавиатура с мышью и геймпад

Геймпад и клавиатура с мышью на равных, переключение на лету: нажал кнопку геймпада (или стик дальше 0,35) — подписи, фокус и курсор сразу геймпадные; клавиша, кнопка мыши или сдвиг мыши больше ~4 px — обратно. Значки кнопок пока текстом («[A]»), названия по Xbox. Все действия — действия InputMap (`game/Input/InputActions.cs`), раскладка геймпада и пункты, ждущие решения владельца, — в `GamepadLayout` того же файла.

| В бою | Геймпад | Клавиатура и мышь |
|---|---|---|
| Движение | левый стик (мертвая зона 0,2; до 0,6 шаг, дальше бег) | WASD / ЛКМ по полу |
| Слоты 1–5 (канал — удержание) | X, A, B, Y, RT (нажат при 0,5, отпущен при 0,3) | 1–5 |
| Подойти к цели | LB | F, ЛКМ по манекену |
| Следующая цель («Рой») | RB | Tab |
| Зум / зум по умолчанию | правый стик вверх-вниз / R3 | колесо / средняя кнопка |
| Пассивки / Скиллы / Разбор / Измеритель | крестовина ← / → / ↑ / ↓ (открыть; открытое без фокуса — закрыть) | P / K / R / T |
| Остальные окна, выбор манекена | Menu: фокус на верхнюю панель | C / N / B / M / L / G, клик |
| Фокус бой ↔ окно (окна не закрываются) | View | — |
| Закрыть верхнее окно | B на верхнем уровне окна | Esc |

Мышь: ЛКМ по полу — идти туда, удержание ЛКМ — бежать за курсором, ЛКМ по манекену — подойти на ближний бой. Скилл, прошедший досягаемость, всегда летит в манекен (курсор задает только движение). Колесо над сценой — зум, средняя кнопка — зум по умолчанию. Клавиши боя не срабатывают, только пока фокус стоит в поле ввода (сид, импорт, уровень скилла); Enter, Esc или клик по полу снимают фокус. Клик, колесо и перетаскивание над окном достаются окну и не двигают героя и не зумят камеру. Открытое окно само бой не останавливает. Переход фокуса в окно отменяет маршрут к цели и удержания боя. Потеря фокуса приложения также сбрасывает удержания камеры и навигации окон; начатая анимация завершается.

В окне с фокусом все кнопки геймпада принадлежат окну (герой стоит, канал отпущен, бой идет): крестовина и левый стик — фокус, A — нажать, B — шаг назад, на верхнем уровне закрыть окно (фокус в бой), LB/RB — кольцо окон (пассивки, скиллы, разбор, измеритель, персонаж, асцендант, прочие открытые), правый стик — прокрутка. Внизу окна строка кнопок говорит, что делают X, Y, LT/RT здесь. Дерево пассивок: стик — ближайший узел в направлении, A — взять или снять, X — атрибут, LT/RT — масштаб, R3 — «Вписать». Скилл: A на «+» — очко, X — снять. Числа: ←/→ шаг, LT/RT ±10; уровень скилла — правка между двумя A (B откатывает). Сид: ←/→ ±1, X — случайный. Измеритель: A на полосе — разбор, Y — «Сбросить» (фокус на «Отмена»). Журнал: Y — к последней строке. Код билда без клавиатуры — «Копировать код» и «Вставить из буфера». Подсказки — одна и та же панель по наведению мыши и по фокусу геймпада.

### Измеритель, журнал и графики

В тренировочной комнате новый выбранный скилл сразу получает максимальный уровень и полный бюджет очков своего дерева независимо от уровня персонажа: родной — 20, скилл из лута — его собственный кап с учетом предмета. Игрок распределяет очки сам; требования и взаимоисключения узлов действуют. Опыт за манекен не начисляется. Уровень можно вручную понизить для сравнения; импорт билда сохраняет заданные в нем уровни. Правила прокачки использованием и отдельного забывания в обычной игре зафиксированы в основной дизайн-спеке §8.2–8.3; игровая прогрессия еще не подключена.

**Измеритель (T)** — полосы в духе Details! за **сегмент боя**: от первого удара до 5 с без ударов (хранятся последние 10, верхний в списке — текущий, за ним измеритель следит сам). Режимы: «DPS по скиллам», «Урон по скиллам», «Урон по типам», «Потеря на защите» (сколько урона съели броня, сопротивления и множитель получаемого урона манекена; бонус от уязвимости, например шока, — отдельная полоса «+N от уязвимости», поэтому проценты этого режима не обязаны давать 100). DPS сегмента = урон сегмента / его длительность; все числа — итоговый урон ядра. Клик по полосе (A на геймпаде) открывает «Разбор» того же числа. Правка билда посреди боя перезапускает бой и открывает новый сегмент «после правки билда» с разницей DPS к прошлому («DPS +4%»). В измерителе же — «Случайность: бросок / среднее» с сидом (смена перезапускает бой), «Сбросить» (спрашивает подтверждение) и переключатель всплывающих чисел урона.

**Журнал (L)** — строки боя по сегментам: применения, попадания с типами урона, отказы нажатий («Перезарядка 2,1 с», «Не хватает ярости», «Вне досягаемости», «Цель не видна»), тики недугов (скрыты по умолчанию, суммируются). Фильтры по виду строки и по скиллу, автопрокрутка; прокрутка вверх ее останавливает. Суммы урона журнала по сегменту равны измерителю (это проверяет самопроверка). **Графики (G)** — для сегмента измерителя: урон по времени (весь и по скиллам), DPS по скиллам, урон по типам и разложение защиты по скиллам.

### Известное поведение и отложенное

- **Жизнь манекена бесконечная у всех пресетов** (решение владельца, спека §6.2а): ядро получает переопределение здоровья, а для условий и плашки у цели есть конечная «подставная» жизнь, которая доливается до максимума. Поэтому условия «цель ниже X % жизни» включаются **циклически**: жизнь опускается ниже порога, бонус работает, жизнь доливается — бонус пропадает. На «Рое» эффекты убийства и возрождения не срабатывают, DPS «Роя» в комнате ниже, чем в мгновенной симуляции (M), которая считает пресеты как есть.
- **Отложено** (решения владельца, позже): модификаторы манекена; летальный режим (манекен умирает); ручной набор сида с геймпада (до экранной клавиатуры сид с геймпада — только ±1 и «Случайный»); значки кнопок PlayStation; значки Kenney Input Prompts (пока текст «[A]»); радиальное меню окон, вибрация, переназначение кнопок.
- Физический геймпад самопроверка не трогает (события синтетические): сценарий спеки §10 п.8 владелец проходит руками.

### Самопроверка

Самопроверка сцены (`-- --selftest`, лимит 300 с) нажимает настоящие панели теми же обработчиками, что и мышь, печатает по строке на шаг (`SELFTEST OK …` / `SELFTEST FAIL …: причина`) и выходит с кодом 0, если все шаги прошли, иначе 1. Она проходит и с полными ассетами, и без них (пустая папка в `DIALOID_ASSETS`: заглушки), и с `-Quality low`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/godot_check.ps1 -SelfTest
powershell -NoProfile -ExecutionPolicy Bypass -File tools/godot_check.ps1 -SelfTest -Quality low
# то же вручную, из корня репозитория
& 'C:\Users\sibiya666\Tools\Godot_v4.7.2-stable_mono_win64\Godot_v4.7.2-stable_mono_win64_console.exe' --headless --path game -- --selftest
```

Приемка (спека §15.4) входит в самопроверку. Для каждого из шести основных эталонов билд загружается во вкладке «Билды» (история «Разбора» при этом очищается), «Тренировочный» манекен считается в режиме «среднее» во вкладке «Симуляция», и DPS панели сверяется с `Simulator.Run` по тому же файлу (до бита). Затем меняются два узла главного скилла (скилл с наибольшим DPS):

- **узел дерева скилла:** кнопкой «−» во вкладке «Скиллы» снимается очко с узла, названного в разборе множителя урона попадания (`hit_mult_*`): DPS меняется, строка узла в этом разборе меняется или пропадает, «+» возвращает DPS точно. Если «−» у всех таких узлов отклонен (на них держатся зависимые узлы, так у огненного Рассекающего удара), берется узел из разбора крита или пробивания, и таблица называет отклоненные; если подходящего узла нет совсем, шаг падает;
- **notable пассивного дерева:** кликом по дереву снимается взятый notable, названный в разборе главного скилла: DPS меняется, в «Разборе» пропадает строка узла, после возврата DPS прежний. Если у билда нет notable, снятие которого не рвет путь к старту (так у «Чародей, Криомант — Ледяное копье»), в таблице стоит «—», другой узел не подставляется.

Итог — таблица `SELFTEST TABLE билд | главный скилл | DPS до | узел скилла «−» | notable`. Еще самопроверка проверяет, что подписи пассивного дерева не перекрывают друг друга и узлы (подпись, которой некуда встать, видна при наведении).

Приемка комнаты (спека §10.5) — тот же прогон. Шаг `acceptance.room-six-references`: каждый из шести эталонов 5 с бьет «Тренировочный» манекен синтетическими нажатиями клавиш 1–5 (режим «среднее», бой с нуля); журнал сегмента не пуст, сумма DPS по скиллам равна DPS сегмента и сумме урона журнала / длительности сегмента (относительный допуск 1e-6), урон измерителя равен сумме журнала; скилл на перезарядке отклоняется (строка в журнале и текст над героем); в окне пассивок снимается узел, те же нажатия дают новый сегмент «после правки билда» с другим DPS. Итог — таблица `SELFTEST ROOM …`. Пункты про геймпад (стик, X, крестовина, A, View, B, LB/RB, достижимость всех элементов окон, переключение устройства) — шаги `gamepad.*`.

Скриншоты снимаются в окне, не в `--headless` (лимит 600 с). Итоговый набор — в `docs/superpowers/debug-scene-screenshots/` в кадре 2560×1440 (если экран меньше, окно все равно 2560×1440 или кадр рендерится в 2560×1440 и масштабируется в окно — строка `SELFTEST NOTE кадр …`): окна плана 3 (`01`–`08`), бой с открытыми журналом и измерителем — зум по умолчанию, ближний на «Боссе», дальний (`10`–`12`), огненный скилл (`13`), «Рой» (`14`), «Рой» со всеми эффектами в перекрестных тенях факелов (`15`), каждый пресет (`20`–`25`), вспышка каждого типа урона на «Бронированном» (`30`–`34`), графики (`40`), пассивки поверх комнаты (`41`), режим геймпада (`50`–`52`). Итоговые снимки — JPEG (качество 92: PNG 2560×1440 весит ~3,5 МБ, набор ~90 МБ на каждую пересъемку); снимки для ревью задач — PNG в `review/` той же папки (вне git).

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/godot_check.ps1 -Screenshots docs/superpowers/debug-scene-screenshots
```

Нагрузка (спека §10.8): `-Perf` в окне держит «Рой» со всеми эффектами (числа, недуги, свет снарядов, тени факелов, журнал и измеритель открыты; v-sync выключен) 20 с после 3 с разогрева в двух сценах — самый частый скилл шести эталонов и самый частый снаряд со своим светом — и печатает `SELFTEST PERF … avg=… fps worst1%=… fps` (худший 1 % — среднее по самым медленным 1 % кадров). Высокое качество меряется в 2560×1440, низкое — в 1920×1080. Приемка: худший 1 % при 1440p не ниже 60.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/godot_check.ps1 -Perf
powershell -NoProfile -ExecutionPolicy Bypass -File tools/godot_check.ps1 -Perf -Quality low
```

Коды выхода `tools/godot_check.ps1`: 0 — всё в порядке; 1 — не прошла сборка или импорт, в логе Godot есть строка `ERROR:`/`SCRIPT ERROR:` (после снятия ANSI-кодов), или с `-ExpectLoadFailure` данные загрузились; 2 — Godot не найден или неверный аргумент; 3 — сцена не загрузила данные игры (строка `DIALOID_LOAD_FAILED:`); с `-SelfTest`/`-Screenshots`/`-Perf` — код самопроверки (он важнее проверок лога); 124 — шаг не уложился в лимит времени.
